Slide 2 · What V4.4 actually is

A diagnostics layer, not a new model

Origin: BBG ESMA COT was tested and dropped

V4.4 was originally going to add new BBG fields (ESMA COT positioning, vol surface). Both regressed vs V4.3:

  • 5-feature COT add: EUA h=3 PT p 0.008 → 0.032, Sharpe +0.89 → +0.68
  • 1-feature trim (SPEC_NET_PCTGROSS only): same regression pattern
  • Vol surface: structural 2-year hole in the BBG pull (MO1 empty 2021–23, TZT1 empty 2022–23) — needs re-pull, not a modeling issue

Diagnosis: collinear with the MF_COT_EUA_* block V4.3 already uses. No orthogonal signal. Reverted V4.4 to a clean wrapper.

What V4.4 became: Track 4 driver

Re-purposed as the diagnostics module for V4.3. Imports V4.3 unchanged, then runs four robustness checks on every cell V4.3 selected:

  1. #1 Safe-fit wrapper — catch extraction-side L3 failures so the pipeline does not crash
  2. #2 Bootstrap CIs — block bootstrap on every CV metric, 90% intervals
  3. #3 Per-regime slice — which Markov regime carries each L3 win?
  4. #4 Rolling-window CV — does the win survive a fixed two-year training window?
Why this matters: V4.3 made claims like "TTF h=1 L3 beats naive by 9% RMSE, DM p=0.028." Track 4 asks: how confident are we? A point estimate that looks great can still be a single noisy walk-forward draw. Bootstrap, regime, and rolling tests separate genuine edges from happy accidents — exactly the kind of disclosure K2's traders need before sizing on a model.

Slide 4 · Track 4 #1

Safe-fit wrapper for L3 final fit

The problem

V4.3 already preserves L3 CV preds when the final-fit fails (see slide on POWER h=1 in the V4.3 deck). But the original fit_layer3() still raised on extraction failures — smoothed_marginal_probabilities can throw if the EM landed in a degenerate corner. A single uncaught throw aborts the whole multi-cell run.

The fix

_safe_fit_layer3(d, market, h, l1, best): try: return fit_layer3(...) except Exception as e: print(" L3: final-fit extraction raised " f"({type(e).__name__}: {e}) — CV metrics retained") return None

Drop-in wrapper at the single call site in train_all_v43(). CV metrics are already separately computed; losing the full-history fit is a per-cell event, not a pipeline event.

Validated live this run

During the rolling-CV run, EUA h=1 hit a real extraction failure on the full-history L3. With the wrapper in place, the pipeline:

  • Logged the exception type and message
  • Kept the CV-window L3 metrics (RMSE 0.02134, DM CI [−0.40, +2.90])
  • Marked the cell as "no full-history L3 fit available"
  • Continued through the remaining 8 cells without interruption
Track 4 #1 cost: ~10 lines of code. Track 4 #1 benefit: a single Markov-EM hiccup no longer kills a 30-minute pipeline run. This is defensive plumbing, not a modeling change — but without it, the bootstrap and rolling sweeps would have failed mid-run on the EUA h=1 cell.

Implementation: _safe_fit_layer3() in K2E_Model_V4_3.py.

Slide 5 · Track 4 #2 · methodology

Block bootstrap on CV metrics

Why bootstrap?

V4.3 reports a single number per cell ("RMSE −9.0% vs naive, DM p=0.028"). That number is one realised draw of the CV process. Bootstrap asks: if we resampled the test windows many times, where would that number land 90% of the time?

Why block bootstrap?

Test predictions are h-step-ahead overlapping forecasts — adjacent observations are correlated. Plain row-bootstrap underestimates variance. Circular block bootstrap with block_size = h+1 preserves the local correlation structure.

B = 1000 bootstrap reps block_size = max(2, h+1) α = 0.10 → 90% CI on RMSE, RMSE-vs-naive %, DM stat, DA, PT stat, EV/trade, Sharpe*

Reading the CIs

  • RMSE-vs-naive CI excludes 0 on the negative side → genuinely better than naive at 90%
  • DM CI excludes 0 on the negative side → DM-significant outperformance at 90%
  • DA CI excludes 50% → directional accuracy genuinely above coin-flip
  • PT CI excludes 0 on positive side → real directional skill
  • EV CI excludes 0 → positive expected return per trade
What "robust" means here: the CV draw V4.3 produced is consistent with the bootstrap distribution. It does NOT prove the edge holds out-of-sample on new data — that's what rolling CV (Step #4) addresses. Bootstrap quantifies sampling noise within the test windows we already observed.

Implementation: _block_indices(), _bootstrap_stat(), bootstrap_rmse_cell(), bootstrap_sign_cell() in K2E_Bootstrap.py.

Slide 9 · Track 4 #3 · methodology

Per-regime L3 diagnostics

The question

L3 is a Markov-switching model — at every observation it has a probability of being in each hidden state. When L3 wins (or loses) on a cell, which regime is doing the work? Is the edge in the calm 90% of days, or the volatile 10%? Are some regimes actively dragging the average down?

The procedure

  1. Pull smoothed state probabilities from the full-history L3 fit (fitted[(market,h,'L3')]['smooth_probs']). State columns are pre-ordered low-vol → high-vol by V4.2's _order_states.
  2. Hard-label each row by argmax(smooth_probs, axis=1).
  3. Recompute the CV test indices via get_cv_folds(n, 3) — the same splits L3's CV uses — so we know which rows the CV preds correspond to.
  4. For each state k, compute RMSE / DA / vs-naive over the CV test rows whose regime label is k.

Important caveat

Smoothed states are full-history hindsight assignments. They are not the per-fold inferred state at forecast time. So this is a diagnostic slice — "in periods the trained model identifies as regime X, how good were the CV forecasts that fold-time models produced?" — not a deployable per-state edge claim.

What we report per cell

  • State σ (sqrt of regime variance) — how distinct are the regimes?
  • Transition diagonals p(k→k) — how persistent is each regime?
  • Full-sample vs CV-window regime occupancy %
  • Per-state n, RMSE, naive RMSE, vs-naive %, DA

Implementation: _state_label_per_row(), _cv_test_indices(), _per_state_metrics(), regime_diag_all() in K2E_RegimeDiag.py.

Slide 12 · Track 4 #4 · methodology

Rolling-window CV vs expanding-window

The asymmetry V4.3's CV has

V4.3 uses expanding-window walk-forward CV: each fold trains on rows[0:ts], tests on rows[ts:te]. Late folds have seen the early data plus everything since.

This is honest walk-forward, but it doesn't tell us whether the win at TTF h=1 L3 survives if the model only sees the most recent N days — which is the situation a deployed system actually faces (data drifts; old training rows become less relevant).

Rolling-window CV

Same test windows. Same model spec (α from V4.3's L1, best (k,s,SV) from L3 sweep, C from sign logit). The only change is the training set is capped at train_window=504 trading days (~2 years).

def _rolling_folds(n, n_folds, train_window): fold = n // (n_folds + 1) for f in range(n_folds): ts = fold + (f+1)*fold; te = ts + fold train_end = ts train_start = max(0, train_end - train_window) yield (train_start, train_end, ts, te)

The decision rule

  • If a cell's expanding and rolling metrics are close (Δ<~5% RMSE, Δ<~3pp DA), the edge is robust to training-history length.
  • If rolling collapses while expanding wins, the edge is partly an artefact of deep history that the live system wouldn't have at deployment time.
  • If rolling improves, the model probably benefits from forgetting old data — possibly a regime-shift or data-quality story in the early years.
Why 504 days: ~2 trading years is the K2 desk's working horizon for "recent enough that the data-generating process probably hasn't structurally shifted." Shorter windows starve L3 of regimes; longer windows defeat the purpose.

Implementation: rolling_cv_l1(), rolling_cv_l3(), rolling_cv_sign(), rolling_all() in K2E_RollingCV.py.
