Forecasting Pipeline — Progress Update

European energy futures (TTF gas, German power, EUA carbon) · 1/3/5-day-ahead forecasts

Status: Production pipeline frozen; robustness audit complete  ·  2026-04-21  ·  Jeff Lu (jl344@fordham.edu)

1. The project in one paragraph

K2 Energy asked us to build a unified short-horizon forecasting pipeline for the three interconnected European energy markets they trade — Dutch TTF natural gas, German baseload power, and EU emission allowances (EUA carbon credits) — at 1, 3, and 5 trading-day horizons. That's nine forecast cells in total (three markets × three horizons). The deliverable is not "the highest possible R²"; it is per-cell honest disclosure: which cells the model can actually beat a simple benchmark, and which cells it cannot. The pipeline ships two parallel models per cell — one that predicts the magnitude of the next move, and one that predicts the direction — plus a referee that decides whether either model is trustworthy enough to use.

2. A few terms used throughout this document

Naive baseline
The simplest possible forecast: "tomorrow's price change will be zero" (i.e., the price stays the same). Sounds trivial, but for short horizons in liquid markets it is famously hard to beat — most of the daily move is unpredictable noise. Every metric in this document is reported relative to this naive forecast. A model has to be meaningfully better than "no forecast at all" to be worth deploying. When you see "vs naive: −9%", that means our model's typical error is 9% smaller than just guessing zero.
Forecast cell
One (market, horizon) combination. E.g., "TTF gas at 1-day-ahead" is one cell. We have nine cells total.
Magnitude vs direction
Two different forecasting problems. Magnitude = "by how much will the price move?" (judged by squared error). Direction = "will the price go up or down?" (judged by hit-rate). A trading desk uses these differently — magnitude for sizing, direction for entry signals.
Walk-forward / rolling validation
How we score the model honestly. We never let the model see the future: it is trained on data up to day T, evaluated on days T+1 onward, then re-trained as time advances. Two flavours: expanding (training set keeps growing) and rolling (training set is capped at the most recent ~2 years). We test both.

3. How the pipeline is built

For each of the nine cells, four components run in sequence:

Step 1 — Linear model
Ridge regression
A regularised linear regression that uses all ~70 features. Fast, transparent, and gives us a feature-importance ranking that the next step uses.
Step 2 — Regime model
Markov-switching regression
A non-linear model that lets coefficients change with the market regime (calm vs volatile). Uses only the top-K features identified by Step 1.
Step 3 — Referee
Best-of-cell policy
For each cell, the policy compares Step 1, Step 2, and the naive baseline on out-of-sample error. Any model that is statistically worse than naive is rejected outright; otherwise the best is selected.
Parallel — Direction
Sign classifier
An entirely separate model that only predicts up vs down. Same input features. Scored on hit-rate and a directional skill test (Pesaran-Timmermann).

Inputs: ~70 engineered features built from ~190 raw columns. The initial ~100 rows of source data were provided by K2E from their existing trading-desk feed (their proprietary dataset is the foundation of the project); we extended it with additional Bloomberg market data, ESMA trader-positioning reports, GIE gas-storage levels, weather forecasts, and physical gas/power flow data. Lags are enforced so the model never uses information it could not have had at the time of forecast. Implementation files: K2E_Model_V4_3.py (main pipeline), K2E_Model_V4_4.py (robustness wrapper), plus three diagnostic modules.

4. How we got here — the process journey

The current pipeline is the result of several deliberate stages, each one a response to a problem the previous stage exposed. The two early-stage write-ups (K2E_model_explainer.html and K2E_results_explainer.html) document where we started and explain how the architecture got pruned to its current shape.

Stage 0 — Setup
K2E provided the foundational dataset.

The starting point was a curated set of ~100 source-data fields from K2E's own trading desk (price history, fuel relationships, COT positioning, physical-flow indicators). This is what every later experiment was built on. From there we layered in additional Bloomberg, weather, storage, and ESMA feeds to grow the engineered feature set to ~70 model-ready features.

Stage 1 — Exploration
Four-layer model bake-off.

The first modeling stage compared four candidate model families head-to-head: a Ridge linear baseline, a high/low-volatility-state Ridge, a GARCH-weighted Ridge, and a Markov-switching regime model. This is the architecture documented in K2E_model_explainer.html and scored in K2E_results_explainer.html. Three findings shaped everything after: (a) the volatility-split model was almost always the weakest — a binary high/low classification was too crude; (b) the GARCH-weighted variant matched the baseline but rarely improved on it meaningfully; (c) the regime-switching model was the most interesting but also the most uneven. We kept only the linear baseline and the regime model, and dropped the two intermediate layers.

Stage 2 — Streamlining
Two-layer baseline (linear + regime model).

With the architecture pruned to two layers, we re-validated more carefully and found two new problems: (a) some "winning" cells were actually worse than the naive baseline once we looked closely (one cell was 10% worse but still being reported as a win); (b) the regime model occasionally failed to fit and silently dropped entire cells from the results.

Stage 3 — Discipline
Added the referee — no architecture change.

Built the referee component (Step 3 above) to force per-cell honesty: any model not beating naive at statistical significance is rejected. Fixed the silent-drop bug so weak cells now get reported instead of disappearing. This is the version currently treated as the production deliverable. Result: 2 cells beat naive on magnitude, 2 cells beat naive on direction, the remaining 7 cells get routed to the naive forecast — which is itself a useful, honest output.

Stage 4a — Data expansion
New data sources tested and dropped.

Tried adding two new Bloomberg feeds: trader-positioning reports and an options-implied volatility surface. The positioning data regressed our results on the EUA market — diagnosis was redundancy with positioning features we already had. The volatility surface attempt was blocked by a 2-year gap in the Bloomberg pull (a vendor-side issue, not a modeling issue). Both attempts are documented as clean negative results so we do not repeat them.

Stage 4b — Audit
Robustness audit on the production pipeline.

With no model improvement to ship, we used this stage to stress-test the existing one. Four checks: (1) wrap the regime fit so failures degrade gracefully instead of crashing; (2) run a block-bootstrap to put confidence intervals on every reported metric — does the win survive resampling?; (3) slice the regime model's errors by regime — does the skill come from one specific market state?; (4) re-validate using a rolling 2-year training window instead of an ever-growing one — does the win survive when the model can't lean on deep history? Result: production results held up on the cells that mattered most, and the referee's rejections all proved correct under the new tests.

8. A few methodologically interesting findings

Regime-bound directional signal (German power, 3-day)

The regime model produces a strong directional signal here, but the standalone direction classifier on the same features cannot. Slicing by regime explained why: in the calm regime, hit-rate is 60%; in a small mid-volatility regime, 75%; in the high-volatility regime, only 36% (signal inverts). The directional skill lives inside the regime structure, not in the raw features. Natural follow-up: build a classifier that conditions its output on the inferred regime.

Regime degeneracy in three configurations

For three cells, the hyperparameter sweep selected configurations where the regime model's "different regimes" turned out to have identical volatilities — so the regimes only differ in their coefficients, which is harder to interpret economically. Suggests a sensitivity check forcing distinct regime variances.

Clean negative result on positioning data

Five candidate features built from Bloomberg's ESMA trader-positioning data all degraded EUA performance. Diagnosis: collinearity with positioning features already in the pipeline (different vendor source, same underlying signal). Documented so we don't relitigate it. The data plumbing was kept in place in case a future interaction or regime-gated experiment can extract orthogonal value.

Independent validation of the referee

The referee component was originally designed using the expanding-window validation. The new bootstrap and rolling-window tests are independent of that protocol — and both independently confirm every rejection the referee made. This means the referee rule itself has external validation, not just the cells it accepted.

9. Feature inventory and model selections

The model sees three distinct pools of input data. Each feature in the pipeline comes from one of these three sources:

K2E dataset

The foundational data feed K2E provided: front-month and CAL-1 market prices (TTF, POWER, EUA, coal, Brent, JKM, NBP), weather and demand fundamentals, physical gas/power flows, COT positioning, and coal-gas switch levels. All BM_, IM_, MF_, and DERIVED_ raw columns. Covers 2021–2024.

Bloomberg (V4.2)

Additional Bloomberg terminal pull added in V4.2: TTF/NBP/EUA term-structure spreads, EUA implied volatility and auction premium, EUA/TTF open-interest and volume changes, French nuclear output, Rotterdam coal return, and the Baltic Dry Index. All BBG_-prefixed features. Sourced from KtE_BBG_Data_Extract-1.xlsx.

GIE API (V4.1)

EU and German gas-storage data pulled daily from the GIE AGSI+ API via gie_fetcher.py, added in V4.1: storage fill levels, injection/withdrawal flows, day-of-year deviations, and German facility outage volumes. All GIE_-prefixed features.
